## 1. 规划背景与目标（作为单独页）

### 第一页
标题：业务现状

业务特征：
├── 项目类型：软件实施 / AI 智控 / 运维服务（3 类）
├── 交付形态：软件 + 硬件 + 服务（复合）
└── 商务节奏：试用 → 验证 → 正式合同（长周期）

现有系统：
├── PMS：已建 9 模块（需求/调研/方案/实施/立项/计划/报工/运维/客户）
├── 用友财务：计划建设（总账/应收/应付/固资/物资/税务）
└── 缺口：业务-财务断点（手工对接、Excel 中转）


### 第二页
标题：业财融合建设目标

总目标：3 句话讲清楚
├── 1. PMS 做业务前端 + 经营分析平台
├── 2. 用友做财务核算准
└── 3. 两者通过发票/收付款对接，业务-财务贯通

分阶段目标：
├── 一期（2个月）：业务台账上线 + Excel 对账
├── 二期（1个月）：用友 API 对接 + 凭证回写
└── 三期：经营分析 + 智能预警

### 第三页
标题：核心设计原则

在满足业务、财务合规的前提下，尽量缩短业务流程、减少审批流。

| 原则 | 说明 |
|---|---|
| 项目为主线 | 项目是业务与财务共同载体，合同、收入、支出、成本、回款都要能归集到项目 |
| 合同收款计划为开票主线 | 开票申请统一参照合同收款计划，简化业务操作，避免验收单、发票、收款计划多头匹配 |
| 收入台账不等于财务应收账款 | PMS 管收入回款台账，用友管正式财务应收和往来账 |
| 支出台账不等于财务应付账款 | PMS 管业务已发生的待付款和成本，用友管正式财务应付和凭证 |
| 发票不是业务发生的唯一依据 | 收入、成本、待收、待付应基于合同、验收、结算、入库、报销等业务事实识别 |
| 发票必须关联业务来源 | 发票不作为所有流程起点，但必须关联收款计划、支出单据或待付款台账，便于业财对账 |
| 先轻量闭环，后深度集成 | 一期先保证业务可用、台账清晰、Excel 可交接；二期再做用友接口和自动回写 |

## 2. 业务融合架构及场景规划（作为单独页）

## 第四页
标题：业务融合整体架构
以项目为核心，将业务流、票据流、资金流、报表流穿起来，形成可追踪的业财融合闭环
业务流：项目经营-合同管理-采购/报销-物资资产-服务/验收
票据流：开票申请-销项发票-采购收票-票据回写-税负统计
资金流：收款计划-收入回款台账-付款申请-支出付款台账-资金计划
报表流：成本归集-收入结构-费用结构-预算执行-管理看板

核心闭环：业务事实-经营台账-发票收付-财务凭证-管理分析

## 第五页
标题：业务融合功能架构

功能围绕项目、收入、付款、物资、研发、集成、经营分析七条主线展开

7 主线的关系：
项目（核心载体）
  ├── 收入回款（项目的"卖"侧：合同→开票→收款）
  ├── 采购付款（项目的"买"侧：采购→入库→付款）
  ├── 物资资产（项目的"物"侧：物资→领用→固资）
  ├── 研发（项目的"投"侧：研发投入归集）
  ├── 财务集成（项目的"财"侧：用友对接）
  └── 经营分析（项目的"管"侧：看板+预警）

项目经营：项目需求、调研问卷、项目方案、项目实施通知、立项计划、运维监控
收入回款：收入合同、收款计划、触发规则、收入回款台账、开票申请、收款核销
采购付款：采购申请、支出合同、采购订单、入库验收、服务结算、支出付款台账、采购收票、付款申请
物料资产：物资台账、日常领用、项目领用、资产台账、资产分配、资产分摊、盘点/调整
财务集成：主数据、发票、支出付款台账、收入付款台账、收款、付款、状态回写
经营分析：税负统计、费用结构、收入结构、预算执行、资金计划、财务回报

PMS业财中台：
统一主数据：客户、合同、项目、供应商、科目、部门、员工
统一业务规则：流程、审批、权限、预警
统一数据模型：业财一体、口径统一、多维分析
统一服务能力：API服务、消息服务、任务调度

系统集层：
用友财务系统：总账、应收、应付、固定资产
AI-OS工艺智控系统：智能体状态、智能体服务有效期

数据支撑层：
数据标准与口径管理：统一定义、统一口径、统一指标
数据质量与治理：数据校验、清洗去重、质量监控
数据安全与权限：分级授权、数据脱敏、访问审计
日志与监控：操作日志、异常告警、运行监控

## 第六页
标题：业财融合数据整体交互
围绕主数据、业务单据、经营台账、发票收付和凭证结果建立双向一致

主数据先统一
客户、供应商、部门、员工、科目、核算主体等基础信息在 PMS 和用友之间同步，避免同一个客户、项目、供应商在两个系统里口径不一致。

PMS 产生业务事实
项目、合同、采购、物资、报销、研发等业务在 PMS 发生，形成业务单据。
这些是后续台账、开票、收款、付款和分析的业务源头。

业务事实沉淀到台账中心
收入合同、收款计划、采购订单、支出合同、入库验收、付款申请等，沉淀为收入回款台账、支出付款台账。
台账的作用是把零散业务单据变成可跟踪、可对账、可分析的经营数据。

发票收付形成财务关键动作
开票、收票、收款、付款、核销等动作围绕台账发生。
例如收入侧：收入合同 → 收款计划 → 开票申请 → 销项开票 → 收款核销。
支出侧：采购订单/支出合同 → 入库验收/服务结算 → 采购收票 → 付款申请 → 付款核销。

用友完成财务核算
PMS 把业务单据、台账、发票、收付款结果推送给用友；用友生成凭证、总账、辅助核算、资产卡片等财务结果。

财务结果回写 PMS
用友把凭证号、凭证状态、核算结果、付款/收款状态等回写 PMS。
这样业务人员在 PMS 里就能看到这笔业务是否已入账、是否已付款、是否已开票、是否已核销。

经营分析基于闭环数据输出
最终看收入、成本、费用、现金流、预算、税负、回报率等，不是单看业务系统，也不是单看财务系统，而是看两边对齐后的统一结果。

## 第七页
标题：场景1：项目经营主线

项目从需求到运维的全生命周期管理，是收入、成本、回款、费用归集的共同载体

项目全生命周期：
新客户报备 → 项目需求（指派技术负责人） → 调研问卷 → 项目方案 → 项目实施通知（指派项目经理）→ 项目立项 → 项目计划 → 执行运维 → 项目结项

项目类型 × 合同类型矩阵：
┌──────────┬──────────┬──────────┬──────────┐
│ 项目类型 │ 合同类型 │ 财务处理 │ 收入确认 │
├──────────┼──────────┼──────────┼──────────┤
│ 内部项目 │ 无合同   │ 记录投入   │ 不确认   │
│ 外部试用 │ 试用协议 │ 记录投入 │ 不确认   │
│ 外部正式 │ 收入合同 │ 见票确认 │ 按里程碑/定时/周期 │
└──────────┴──────────┴──────────┴──────────┘

试用项目：项目立项均按正常项目执行，以收入合同类型掌握项目商务状态（未签/试用合同/正式合同）

内部项目：以项目属性区分内部项目、外部项目，便于后续财务结算

是否属于集团项目：集团项目全集团可见，主要作为后续内部结算标识；内部结算合并规则“核算主体+项目名称”

经营洞察：可按项目查看从需求、立项、计划到执行运维的全过程状态，识别项目是否已纳入统一管理等经营风险

## 第八页
标题：场景2：收入回款主线-收入确认

收入合同记录业务事实，再按收款计划触发收入回款台账，形成合同、项目、开票、收款的统一事实

收入确认 5 步：
① 签订收入合同 → PMS 录入合同（金额/条款/收款计划）
② 拆分收款计划 → 按里程碑/分期/一次性
③ 业务确认收入 → 验收/履约达成时点/定时
④ 形成收入回款台账 → 业务侧台账（≠财务应收）
⑤ 用友生成凭证

触发条件：合同签订或生效、收款计划到期、验收节点达成

数据来源：收入合同、收款计划、项目归属、客户信息

业务处理：收入合同必须归属一个项目，合同金额、收款计划、开票和回款均归集到该项目。合同签订时项目暂未明确的，可先进入待归属合同池；合同归属一般由合同负责人沟通完善


规范条件：收入合同原则上必须关联唯一项目，一个项目可关联多个收入合同；验收、开票、收入确认、收款核销前必须完成项目归属

经营洞察：可按项目查看合同金额、收款计划、已开票、已收款、未收款和到期风险，支撑领导判断项目收入进度、回款压力和客户履约情况


## 第九页
标题：场景2：收入回款主线-销项开票

开票申请统一参照收入合同和收款计划，确保发票不脱离项目、合同和业务阶段

开票 6 步：
① 选择收入合同 → 选节点（一次性/多节点合并）
② 发起开票申请 → 自动校验：≤收款计划金额
③ 财务确认 → 检查发票抬头/税号/科目
④ 销项开票 → 财务开票（线下或线上）
⑤ 发票回写 → 发票号/金额/图片 回写 PMS
⑥ 用友生成凭证 

触发条件：合同约定开票、客户要求开票、验收开票

数据来源：收入合同、收款计划、客户水务信息、开票科目

业务处理：选择一个节点和多个节点开票、财务确认开票科目；支持蓝字、红字发票开具

校验规则：
├─ 开票金额 ≤ 收款计划金额（强制）
├─ 开票科目 = 合同约定科目（强制）
├─ 客户税号 = 主数据税号（强制）
└─ 跨期开票：支持提前开票

经营洞察：可查看已开票、未开票、提前开票开票风险

## 第十页
标题：场景2：收入回款主线-收款核销

收款单与收入台账、发票形成核销关系，保障业务发生、发票和资金到账一致

收款核销 6 步：
① 收款登记 → 银行流水导入 或 线下录入
② 系统自动匹配 → 按客户+金额+合同+项目
③ 财务确认 → 检查匹配是否正确
④ 收款核销 → 关联收入回款台账 + 销项发票
⑤ 用友生成凭证
⑥ 容差预警 → 尾差/部分付款/合并付款处理

触发条件：银行到账、客户付款凭证、线下收款确认

数据来源：银行流水、收款单、收入合同、项目档案、客户信息、收款计划、收入回款台账、销项发票、用友凭证

特殊场景：
├─ 预收款：客户先付钱，未开票 → 挂预收
├─ 部分付款：100 万合同只付 30 万 → 部分核销
├─ 合并付款：客户一笔款对应多张发票 → 拆分核销
└─ 尾差：实付 99.99，合同 100 → 容差预警

经营洞察：可按项目、合同和客户查看已收款、未收款、预收款、开票未回款、回款未开票和超期应收情况，支撑判断现金流压力、客户履约风险和催收重点。


## 第十一页
标题：场景3：采购付款主线-物料采购

可入库、可领用、可消耗的实物采购，通过入库形成物料台账和支出付款台账

物料采购 9 步：
① 采购申请 → 项目/部门提需求
② 采购订单 → 选定供应商；采购计划/紧急采购
③ 采购合同判断 → 是否需要合同（金额阈值）
④ 物料入库验收 → 仓库验收（数量/质量）
⑤ 同步生成：物料台账 + 支出付款台账
⑥ 采购收票 → 供应商开发票（关联支出付款台账）
⑦ 付款申请 → 见票付款（付款核销）
⑧ 对公付款 → 银行打款
⑨ 用友生成凭证 

触发条件：项目物资采购、日常物资采购、供应商到货

数据来源：采购申请、采购合同、供应商信息

关键差异物料台账 vs 支出付款台账）：
物资台账：记录"物"的状态（数量）
支出付款台账：记录"钱"的状态（应付/已付/未付）

规范条件：采购类型、项目归属、入库数量和金额必须明确

经营洞察：可查看项目物资成本、物资来源、待收票和待付款压力

## 第十二页
标题：场景3：采购付款主线-服务采购

无实物入库的服务采购，以服务成果、服务过程或人力投入作为交付对象

服务采购 8 步：
① 采购申请 → 项目/部门提需求
② 采购订单/合同 → 选定服务商
③ 服务过程 → 服务商执行
④ 服务结算单 → 验收成果/工作量
⑤ 支出付款台账 → 形成待付
⑥ 采购收票 → 服务商开发票（关联支出付款台账）
⑦ 付款申请 → 按合同约定付款（付款核销）
⑧ 用友生成凭证

触发条件：外包服务采购、服务阶段完成、服务验收通过

数据来源：采购订单、服务成果、结算单、收票信息

业务处理：服务结算后生成支出台账、收票参照支出付款台账、支持挂外部项目与内部项目

规范条件：结算单需说明服务期间、成果、验收责任人和金额

经营洞察：可查看服务成本、待收票、待付款和项目利润影响


## 第十三页
标题：场景3：采购付款主线-固资采购

价值高、使用周期长的实物资产，入库验收后进入用友资产卡片和生成支出付款台账、固资台账

固资采购 9 步（与物资采购的区别：节点③+⑤+⑨）：
① 采购申请 → 固资类目
② 采购订单 → 选定供应商
③ 采购合同判断 → 高价值必走合同
④ 固资入库验收 → 一物一卡（资产卡片）
⑤ 同步生成：固资台账 + 支出付款台账 + 资产卡片
⑥ 采购收票 → 供应商开发票（关联支出付款台账）
⑦ 付款申请 → 见票付款（付款核销）
⑧ 对公付款 → 银行打款
⑨ 用友生成凭证
   （验收时点即生成凭证）
⑩ 折旧分摊 → 用友按月折旧（按部门/项目）

触发条件：高价值资产采购、公司自用资产到货、资产验收通过

数据来源：采购（固资类目）、入库验收单、、固资主数据

业务处理：固资采购以"入库验收合格"为关键时点，验收通过即同步生成财务凭证与资产卡片（一物一卡）；固资折旧对接用友数据；付款申请需要有对应发票

规范条件：资产价值单价大于等于5000元（支持配置）且使用年限大于1年

经营洞察：可查看固资采购规模、供应商与品类分布、验收合格率及折旧对成本的影响


## 第十四页
标题：场景4：物资管理主线

物资管理主要解决物资买入后去向不清的问题，支撑项目成本真实性和资产责任管理

主要流程：物资台账（物料、固资）-项目/部门领用（财务凭证）-物资盘点-物资调整（财务凭证）

触发条件：采购需求、固定资产采购、物料补库、紧急物资申领、安全物资

数据来源：物资入库单（物料、固资）、领用单

业务处理：区分内部物资、项目物资；挂内部项目满足固资条件则为固定资产理，挂外部项目则为项目物资，物料也是同样处理

规范条件：物料单价小于5000元（与固资区分）；按类目编码管理；安全物资预警；领用必须关联项目或部门；自动补物资

经营洞察：可查看物资采购规模、物资周转效率、领用项目分布及物资占用情况

## 第十五页
标题：场景5：费用报销主线

用报销主要解决差旅、招待、日常采购等零散支出的合规管控、入账与项目/部门归集问题

主要流程：
差旅报销：差旅申请单-差旅报销单-支出付款台账-付款单
招待报销：招待申请单-招待报销单-支出付款台账-付款单
日常采购报销：日常报销单-支出付款台账-付款单

触发条件：员工因公出差、业务招待、紧急小额采购、零星办公支出

数据来源： 差旅/招待申请单、日常报销单、发票（专票/普票/电子发票）、付款记录（个人垫付）

业务处理：费用报销以"审批通过"为关键时点，审批完成后按"谁受益谁承担"原则自动归集至项目或部门成本，生成财务凭证，员工垫付款通过报销流程支付。日常采购报销小于1000元可报销，特殊情况特殊处理；日常报销涉及物资直接费用化

规范条件：发票抬头必须为公司；差旅住宿按标准执行（可配置）；招待费需事前申请；报销单必填关联项目或部门

经营洞察：可查看费用结构（差旅/招待/日常）、部门费用占比、报销时效及异常报销预警
