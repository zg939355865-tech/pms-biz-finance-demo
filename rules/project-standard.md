# PMS 项目通用准则

## 1. 适用范围与优先级

- 本文件是 PMS 高保真原型、Schema、页面样例和静态 HTML 的项目级基线。
- 适用于后续所有页面生成、还原、优化和验收；与旧规则冲突时以本文件为准。
- 新页面先匹配 `prototype-resources/index.html` 中的页面样例，再使用已注册组件，不从空白结构自由设计。

## 2. 标准生成链路

```text
自然语言需求 -> AI 生成蓝图 MD -> 用户确认 -> 正式 Schema v2
-> 公共策略生成 Effective Schema -> Schema/策略校验 -> HTML 生成
-> 页面与视觉检查 -> 匹配现有菜单 -> 交付
```

- 蓝图 MD 用于业务确认；正式 Schema 是页面结构、组件、状态、权限和交互的唯一机器输入。
- 可自动判断或统一补齐的公共准则不得只写在规则文档中，必须同步进入 `policies/`、策略引擎或自动检查；新增公共准则至少包含策略配置、执行逻辑、校验规则和回归用例，完整生成命令必须执行这些检查。
- 不生成草稿 Schema，不因新增页面自动修改 Excel 菜单源。
- 页面必须引用公共 Token、组件样式和运行时，禁止复制一套页面私有组件代替公共组件。

### 2.2 布局生成前必须对照参考页面

- 生成页面布局（查询区 Grid、分页结构、汇总行、按钮排列等）前，必须先读取同类型参考页面的实际 HTML 结构，照搬其 Grid 列定位、组件嵌套和 class 用法，不得凭推断编写。
- 查询区按钮排列：读参考页面的 `.pro-search-form-grid` 结构，确认 `data-search-remainder` 值，查询/重置按钮必须通过 `grid-column` 定位到正确列（与上一行最右列对齐），禁止用空 form-item 撑列。
- 分页与汇总结构：读参考页面的 `pro-table-footer` 内部结构，照搬 `pro-table-selection`、`pagination`、`pro-table-summary` 的嵌套层级和 class，禁止自创结构。
- 验证方式：生成后对比参考页面的关键结构片段（footer 内嵌套、按钮 grid-column 值），不一致则重做，不得提交让用户发现。

### 2.3 犯错必须主动写记忆

- 被用户纠正错误或指出不符合规范后，必须立即写记忆到 `memory/` 目录，记录错误现象、根因和正确做法，不得等用户提醒才记。
- 发现用户重复性工作偏好（如"不要说废话直接执行"、"一次做对不要试错"）时，主动写入记忆，下次会话自动加载。
- 写记忆是强制动作，不是可选项。每次会话结束前应检查是否有应记未记的内容。
- **写入记忆后必须在对话中显式输出**：`已写入记忆：[文件名] — [一句话内容摘要]`，让用户当场确认。未输出此句 = 未执行。

### 2.4 任务完成必须输出变更清单

- 每次任务完成后，必须列出本次修改的所有文件路径，格式为清单（文件路径 + 一句话变更说明）。
- 清单必须覆盖：新增文件、修改文件、删除文件，不得遗漏。
- 不得只说"已完成"而不列出具体改了哪些文件。

### 2.5 已有页面变更流程（最优路径）

- 修改已有页面时，**同时修改源 Schema 和 HTML**，不等待生成命令执行。
- 源 Schema 是真相源，保证下次 `verify:page` 生成时变更不丢失。
- HTML 是运行时产物，直接修改保证当下立即生效，无等待成本。
- **禁止修改生效 Schema**（`outputs/effective-schemas/`），它是策略引擎自动生成的，会被覆盖。
- 此方案时间成本最低（两个文件都是秒级修改），且无风险（Schema 保证一致性，HTML 保证即时性）。

### 2.1 增量变更防回退

- 已有页面优化默认只改用户指定区域；禁止为单页局部需求运行会重建同模块多个页面的批量生成脚本。
- 修改前必须读取当前蓝图、Schema、生成页和专项检查作为基线；用户未要求的查询项、列表字段、按钮、详情区域和弹窗必须保持不变。
- 专项检查只能在原检查基础上追加或调整本次断言，禁止用新检查整体替换旧检查、删除非本次范围的既有断言。
- 生成后必须对比修改前后字段及操作清单；发现非本次范围变化时立即停止交付并恢复，不得以生成结果覆盖已确认设计。
- 单页局部需求的检查范围固定为：目标页面 Schema 校验、HTML 结构检查、专项交互回归、1440px/2048px 页面检查及 iframe 菜单入口；不得运行组件覆盖、资源中心、全页面 Harness 或其他与本次变更无关的项目级检查。
- 仅当本次实际修改公共组件、公共样式、公共运行时、公共策略、公共生成器逻辑、资源中心或菜单框架时，才追加对应的项目级检查；项目级检查必须与实际影响范围一一对应，不得以“稳妥”为由扩大范围。

## 3. 页面架构

- 主框架采用固定侧栏、顶部栏、标签页和 iframe 内容区；功能页只包含内容区。
- 列表、新增、编辑、详情优先共用一个 HTML；新增、编辑、详情在页面内切换，不使用弹窗或抽屉承载完整业务页面。
- 弹窗仅用于确认、审核、数据选择等辅助操作。
- 页面必须支持直接打开和 iframe 嵌入。

## 4. 页面头与布局

- 列表页和详情页首行高度、标题基线、左右内边距保持一致，不保留无意义顶部空白。
- 页面标题 20px/600；正文 14px/400；辅助文字 12px/400；全部使用项目字体和 Token。
- 间距采用 8px 系统；按钮圆角 6px、卡片 8px、模态框 12px。
- 页面整体不得左右滚动；宽表只允许表格内部横向滚动。

## 5. 查询区

- 桌面端每行最多 4 个查询项，标签和控件等长对齐；窄屏按 2 列、1 列响应。
- 查询项不足 4 个时仍保留四列基线：条件从左向右排列，查询操作占用当前行剩余栅格并靠右对齐，不将少量条件拉伸成不等宽大控件。
- 查询项多于 4 个时按四列自然换行并全部铺开；不得显示“更多筛选”或“收起筛选”。最后一行不足 4 项时，查询、重置紧随该行并靠右收口。
- 下拉型条件必须使用标准 Select 并显示箭头；项目选择默认使用下拉选项。
- 查询、重置位于查询区末尾，不显示“更多筛选”“收起筛选”、刷新、全屏、列设置等默认工具按钮。
- 不显示“已选择 N 项”等常驻选择提示条。

## 6. 业务主列表

- 表头 14px/400、56px 高；数据行 56px 高；复选框和各列按统一间距对齐。
- 编码、名称、日期左对齐；金额、数量右对齐；状态和操作居中。
- 有流程状态时每个真实状态展示 1 条代表数据；无状态时展示 5 条数据。
- 列表不产生纵向内部滚动；需要宽表时仅表格主体横向滚动。
- 业务字段不超过 6 列的业务主列表由公共 `ProTable` 自动使用均衡列布局，表头和数据居中，列宽平均分布；禁止单页编写私有间距或对齐样式。
- 超过 6 个业务字段的主列表保持标准字段语义对齐，不套用少列均衡布局。
- 宽表需要冻结多个左侧上下文字段时，统一使用公共 `ProTable` 的 `fixed: "left"` 与 `fixedOffset` 按列宽累计定位；禁止页面私有实现冻结列。
- 宽表横向滚动时，左侧复选框列和首个编号/编码/单号列必须固定，最右操作列同时固定；三个固定区域背景必须不透明并遮挡滚动内容。
- 固定编号/编码/单号列宽度保持稳定，表头层级高于固定数据单元格，横向滚动时不得出现文字穿透或重叠。
- 列宽必须按字段语义分档，禁止状态、名称、日期、数值等不同类型字段统一等宽。公共 `ProTable` 默认采用：序号 72px、状态 104px、人员 128px、数值 112px、日期 136px、日期时间 168px、编码 176px、名称 200px、普通字段 160px、长描述 280px。
- 常规字段最大建议宽度为 240px，详情、备注、地址等长文本最大建议宽度为 320px；超出内容统一单行省略并在悬停时展示完整值。
- Schema 仅在业务语义确有差异时使用 `columns[].width` 覆盖公共默认值；`columns[].ellipsis: false` 只用于明确要求完整展示的字段。禁止页面私有实现列宽、截断和悬停提示。

### 6.1 操作列与删除权限

- 所有业务维护主列表必须显示固定在最右侧的「操作」列，横向滚动时位置不变且背景不透明。
- 操作列只保留「删除」，不得显示查看、编辑、提交或审核按钮。
- 每行必须显示「删除」。有流程状态时仅 `草稿` 行可删除，其他状态显示禁用删除；无流程状态时默认可删除。
- 流程单据的草稿通过「删除」撤销，不提供「终止」操作；需要保留历史痕迹的终止仅用于已提交后的非草稿状态，具体可终止状态由页面蓝图和正式 Schema 声明。
- 编号、编码或单号链接是列表进入详情的唯一入口：流程单据 `草稿` 进入可编辑详情，其他状态进入只读详情；无流程状态记录进入可编辑详情。
- 只读报表、监控表、数据选择弹窗、详情页子表不自动继承业务主列表删除规则。
- “我的审批”属于待办办理工作台，不继承业务维护主列表的删除和编码链接规则：仅展示未结束、未终结的待审批记录；不同审批类型不得因流程状态相同而合并；业务单号显示为普通文本；操作列仅显示无跳转、无弹窗的「办理」按钮，不生成详情区域。
- “我的任务”属于只读任务工作台，不继承业务维护主列表的新增、删除和详情入口规则：仅用于查询当前用户负责或参与的任务；不显示复选框和操作列，项目编码等标识字段使用普通文本。
- Schema 主列表必须设置 `keepOperationColumn: true`，`rowActions` 只能包含一个 `delete`；流程删除动作必须设置 `enabledStatuses: ["草稿"]`。
- 由上游业务完成后自动生成、不可人工新增或删除的记录，Schema 必须声明 `systemGenerated: true`：主列表不显示新增按钮、删除按钮和操作列。若该记录支持审核/反审核，使用公共单选状态动作并放在页面标题右上角；待审核记录仅可审核为已审核，已审核记录反审核后默认回到草稿，业务明确要求其他状态时按显式例外执行。
- 业务主列表统一使用公共方形复选框；“仅允许选中一条执行”的限制由动作的 `requiresSingleSelection` 控制，不得把主列表改成圆形单选框。圆形单选框仅用于数据选择弹窗等明确的单选场景。
- 列表业务动作依赖流程状态但页面不要求展示状态列时，使用 `ProTable.statusCode` 声明隐藏状态字段；状态仍必须写入行数据，用于审核、反审核、删除权限和详情模式，不得为驱动权限强行增加可见状态列。
- 批量删除和行删除完成后，公共 `ProTable` 必须同步更新当前行数及分页区“共 N 条记录”，不得保留删除前计数。
- 业务主列表的批量删除按钮统一放在页面标题右上角操作区，并与新增等页面级动作并列；不得放在查询区下方或表格内部工具栏形成额外空白区域。
- 所有必填表单字段及可编辑子表必填列，必须在字段名或列表表头前显示红色 `*`；选填、自动带出及只读计算字段不得显示必填标识。
- 所有启用分页的业务列表必须在总记录数右侧显示固定页容量组件；默认显示“5条/页”，组件仅用于向开发明确分页规格，不提供其他条数选项，不得因切换页容量引入业务区纵向滚动。
- 所有启用分页的业务列表必须始终显示“共 N 条记录”，不得设置 `showRecordCount: false` 或 `showPageSize: false`；未声明时继承公共默认值 `showRecordCount: true`、`showPageSize: true` 和 `pageSize: 5`。
- 业务页面同时包含业务单号/编号和主状态字段时，主状态统一命名为“状态”，并在查询区、主列表和详情基础信息中紧跟业务单号/编号；不得被其他业务字段隔开。类型等业务属性需要紧跟状态时，由页面 Schema 在状态后顺序声明。公共策略引擎必须自动纠正主状态名称和位置，并由策略检查及回归用例强制验证。
- 审核/反审核已明确在列表完成时，详情页通过 `detailReviewEnabled: false` 和 `detailWorkflowLinksEnabled: false` 关闭重复审核及流程入口，详情只保留返回及业务所需保存动作。
- 无流程的录入类详情页统一使用 `detailSaveEnabled: false`、`detailSubmitEnabled: true`，详情头部只显示「返回列表、提交」；不得显示「保存」或「保存草稿」。提交表示完成业务数据保存并返回列表，不发起审批流程。
- 所有非流程页面只要启用提交动作，按钮文案必须统一为「提交」，不得使用「提交审核」「发起审批」等流程化文案；提交后的业务状态变化由单据状态机定义，不改变按钮公共文案。公共策略引擎必须强制覆盖不符合要求的 Schema 文案。

## 7. 详情与表单

- 详情表单桌面端每行 3 个等宽字段，字段不跨行，不用大文本框破坏栅格；确需长文本时单独放在对应业务页签。
- 同一页签不重复显示页签名和区块标题；无必要不显示“基础信息”等重复标题。
- 业务字段从单据基础信息移入明细后，若不再属于整单维度，查询条件和主列表必须同步删除该字段；仅在明确要求按明细汇总查询或展示时保留。
- 附件已作为页签名称时，页签内容区不得重复显示“附件”“申请附件”等同义标题，直接展示上传区域和附件列表。
- 附件列表的上传、删除权限继承当前单据编辑状态：草稿或其他明确可编辑状态允许上传、删除，其他状态仅可查看且删除操作禁用。
- 附件列表统一展示“文件名、大小、上传人、上传时间、操作”，不得展示或保存“资料类型”字段。
- 页签下的新增、选择、拆分等业务按钮放在内容区左侧。
- 草稿状态可编辑；其他状态只读。审核状态通过统一审核按钮打开审核面板，面板内同时提供通过与驳回。
- 无流程录入类详情页不设置草稿暂存，新增和编辑时统一显示「返回列表、提交」；提交完成业务数据保存并返回列表，不产生待审核状态，也不进入审批流程。
- 有流程状态的详情页恢复原状态规则：草稿显示「返回列表、保存草稿、提交」，待审核显示「返回列表、审核」，其他状态显示「返回列表」；保存草稿和提交后返回列表。
- 不设置独立“审核记录”页签；流程动态、当前责任人、流程图从页面右上角流程按钮进入。
- 流程类详情页只保留右上角流程查看入口，内容区不得重复出现“流程动态”“当前责任人”“流程图”页签。
- 详情页签名称已经承担内容分组作用，页签内容区左上角不得重复显示与页签同义的区块标题；内容直接从字段、工具栏或业务卡片开始。仅当同一页签内存在多个必须区分的业务子区块时，才允许使用非重复的局部小标题。
- 系统自动生成且在列表完成审核/反审核的页面，详情基础信息全部只读；可维护的明细页签按业务权限单独开放，不得反向开放基础信息。
- 详情进入查看或其他只读状态时，未录入业务值的输入框、文本域、下拉框、多选框和选择器统一显示为空白，不得显示“请输入”“请选择”等录入提示；新增和草稿编辑状态保留输入提示。
- 点击列表“新增”进入详情时，所有尚未产生的业务字段必须为空，不得继承 Schema 样例值或其他记录数据；仅保留流程草稿状态、项目未开始状态、创建人、创建时间、当前公司等系统自动初始化值。由上游单据选择带出的只读字段，在完成选择前同样保持为空。仅从草稿记录进入编辑时，才恢复并显示该记录已有业务值。
- 不默认增加“业财穿透链路”，仅在业务场景明确需要时使用。
- 表单控件下方禁止常驻字段级辅助文案，包括编号生成规则、自动计算说明、保存或提交逻辑、选填条件、一致性校验等解释文字；正式 Schema 不得依赖 `fields[].help` 呈现此类内容。规则必须保留在蓝图和 Schema `rules` 中，并通过字段状态、选择范围、提交校验或操作弹窗体现；只有用户明确要求持续展示的风险提示，才允许使用独立业务提示组件。
- 页面默认不显示任何点击 Toast；查询、重置、刷新、删除、保存、提交、审核等动作仅执行交互本身。只有具体实现说明明确要求时，才允许通过 `toastEnabled: true` 单页启用。

## 8. 状态与样例数据

- 状态必须来自真实业务或已确认需求，禁止用通用状态替换真实流程。
- 每个真实流程状态至少有 1 条可见样例数据，并验证按钮权限、标签颜色和详情模式。
- 状态标签统一使用项目状态色；日期统一 `YYYY-MM-DD HH:mm:ss`，金额使用千分位和 2 位小数。
- 业务金额、计划金额、收付款金额及财务凭证金额必须保持可解释的一致关系。

## 9. 组件与样例

- 统一入口：`prototype-resources/index.html`。
- 组件注册：`prototype-resources/components/component-registry.json`。
- 页面样例：`prototype-resources/samples/`；公共 Token 和样式：`prototype-resources/components/`。
- 页面只使用注册组件；涉及公共行为的调整必须同步组件、样例、Schema 规则和自动检查。
- 正式业务维护页不得以手写私有布局绕过 Schema 和页面样例；历史页面偏离标准时，先补齐正式 Schema，再由统一生成器覆盖输出 HTML。
- 表格、表单、按钮、Select、Tabs、Modal、Tag、Pagination 等必须使用标准组件样式。
- 行内编辑表格的字段宽度通过公共 `EditableTable` 的 `columns[].width`、`operationColumnWidth` 和 `minWidth` 配置，禁止为单个页面编写私有列宽或间距样式；桌面端宽表使用表格内部横向滚动，不压缩可编辑字段。

### 9.1 历史专用页面兼容

- 驾驶舱、运行监控、流程指引等保留专有可视化结构的历史页面，允许通过公共兼容层渐进接入资源中心，不得继续复制或扩展页面私有基础控件。
- 兼容页面必须引用 `tokens.css`、`components.css`、`legacy-page-bridge.css` 和 `legacy-page-bridge.js`，并声明 `data-legacy-bridge="true"`；大屏页面同时声明 `data-page-theme="screen"`。
- 兼容层统一字体、颜色、间距、圆角、表单控件、按钮、表格及长文本省略行为；页面业务结构和专有图表可保留。
- 新增业务维护页仍必须使用正式 Schema 和已注册公共组件。历史兼容页发生结构性改版时，必须补齐正式 Schema 后由生成器覆盖交付。

## 10. 交互反馈

- 按钮必须具备默认、悬停、聚焦、禁用状态；禁用操作不可触发事件。
- 页面不得常驻展示“修改规则”“录入规则”“归档规则”等解释性信息横幅；业务规则由字段状态和提交校验体现。仅当前风险必须持续可见时，才允许明确声明为持久提示。
- 不显示“已触发：某操作”一类演示提示；仅在真实查询、保存、删除、审核结果后显示简短反馈。
- 删除需执行确认或明确的可撤销演示逻辑；原型中删除成功后同步移除行和更新计数。
- 非流程业务审核单据的“审核、反审核”统一放在列表页头右侧，通过列表单选记录后按状态启用；详情页不得重复放置审核、反审核按钮。
- 非流程业务审核单据反审核默认回到“草稿”；业务已明确要求回到其他状态时，必须通过 Schema 的 `reverseAuditNextStatus` 显式声明。
- 可编辑明细表的行删除和批量删除统一使用“删除”“删除选中明细”文案，不使用“移除”。

## 11. 自动验收

- 自动验收按变更影响范围分级执行：单页局部变更必须通过目标页面 Schema 校验、HTML 结构检查和专项交互回归；组件覆盖、资源中心及全页面 Harness 仅在对应公共能力发生变更时执行。
- 公共策略必须在生成阶段自动补齐并在策略检查中强制验证以下高频能力：业务主列表页头批量删除、业务审核单据的列表页头审核/反审核、流程详情状态按钮、表单及明细必填校验、所有删除动作二次确认、详情表单桌面端三列布局；任一能力缺失时不得交付。
- 公共回归验证必须实际操作上述五项能力，不能只检查规则文档或静态字段是否存在。
- Harness 必须检查 `pages/` 下全部交付页在 1440px、2048px 桌面视口可打开、无页面级横向溢出，并验证公共样式引用及菜单目标存在。
- 页面生成与依赖生成结果的页面检查必须串行执行：先完成 HTML 生成，再执行 Schema、策略和页面检查；禁止并行运行生成与页面检查，避免检查读取旧文件。
- 当前原型交付范围仅验收桌面端，至少检查 2048px、1440px，并检查 iframe 菜单入口。
- 移动端尚未规划，不纳入当前页面生成和验收结论；后续明确移动端范围、断点和交互方案后，再建立独立移动端规则与检查。
- 检查页面整体无横向溢出、列表无纵向内部滚动、操作列横向滚动前后位置不变。
- 检查流程列表：草稿删除启用，所有非草稿删除禁用；无状态列表删除启用。
- 检查生成后无临时脚本、调试状态和重复交付页面。

## 12. 交付要求

- 正式页面存放于 `pages/`，按现有菜单路径匹配入口。
- 每次交付只说明完成状态、文件路径、关键变更和验证结果，不粘贴完整文件。
## 详情页审计字段

- 公司审计字段、`创建人`、`创建时间`属于页面级审计字段，每个详情页只允许出现一次。
- 项目需求等同时存在“需求来源公司”和“项目主责公司”的页面，通用公司审计字段统一显示为“创建公司”；创建公司取创建时右上角当前公司主体，只读且不可修改。
- 项目需求创建时，创建公司必须等于需求来源公司或当时的项目主责公司；后续主责公司正式变更不得回写历史创建公司。
- 项目需求点击提交时，需求来源公司、项目主责公司至少一个必须与创建公司一致；否则阻止提交，并通过公共消息组件提示“不能为别的公司提交需求”。该校验不影响保存草稿。
- 调研问卷、项目方案关联项目需求时，需求编号、需求名称、客户编码、客户名称、需求来源公司、项目主责公司必须由同一条已审核项目需求统一回填；公司字段只读，不允许脱离来源需求单独修改。
- 项目实施通知关联项目方案时，需求编号、需求名称、方案编号、方案名称、客户编码、客户名称、需求来源公司、项目主责公司必须由同一条项目方案统一回填；公司字段只读，不允许脱离来源方案单独修改。
- 审计字段统一放在“基础信息”的主 `DetailForm` 中，不得注入“需求内容”“需求信息”“联系人”“附件”或其他业务 Tab。
- 公共策略只向详情页第一个 `DetailForm` 补齐缺失审计字段；后续 `DetailForm` 出现同名审计字段视为规则违规。
- 已有真实业务值时不得被“当前登录公司”“当前登录人”等默认占位值覆盖。
# 项目需求列表视图

- 项目需求列表使用同一数据源的分类页签，不拆分为多个独立页面。
- 默认页签为“全部需求”；“我司负责”包含“我司主办、我司承接”；“外发跟踪”包含“我司外发”。
- “外发跟踪”页签的操作列提供“查看进度”，携带当前需求编号打开“需求跟踪表”；仅展示授权范围内的需求业务进展，不开放项目主责公司的内部审批过程。
- 分类页签只提供基础视图筛选，不改变数据权限、流程状态和详情入口；查询区“处理类型”等条件在当前页签范围内继续叠加筛选。
