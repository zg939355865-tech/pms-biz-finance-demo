# 页面蓝图 MD 规范

## 1. 目的

本规范用于将用户的自然语言需求转换为可检查、可确认、可继续生成正式 Schema v2 的页面蓝图 Markdown 文件。

页面蓝图是业务确认文件，不是技术实现文件。蓝图中不编写 HTML、CSS、JavaScript，也不嵌入 Schema JSON。

标准流程：

```text
自然语言需求
  -> AI 生成页面蓝图 MD
  -> 用户检查并确认
  -> AI 生成正式 Schema v2
  -> Schema 生成 HTML 原型
```

## 2. 用户与 AI 的职责

### 2.1 用户需要提供

用户只需尽量说明以下内容，不要求填写固定模板：

- 要解决的业务问题或使用场景。
- 主要使用人员。
- 必须支持的操作。
- 已明确的关键业务规则。
- 需要参考的现有页面、截图或系统。

最简需求可以只有一句话，例如：

```text
生成收入合同页面，支持增删改查和审核；一个合同可以关联多个项目，正式合同必须维护收款计划，试用合同不产生收入。
```

### 2.2 AI 必须补充

AI 根据项目规则、菜单、现有页面、组件库和业务上下文补充：

- 页面类型和页面组成。
- 查询条件、列表列、详情字段和表单分组。
- 按钮位置、行操作和批量操作。
- 页面跳转、弹窗、抽屉和页签关系。
- 状态、权限和操作可用性。
- 必填、格式、金额、日期及关联数据校验。
- 加载、空数据、错误、禁用和只读状态。
- 业财关联链路和数据一致性要求。
- 公共组件与现有样例映射。
- 可演示样例数据和验收标准。

### 2.3 AI 不得擅自确定

以下内容没有依据时必须列入“待确认项”，不得作为已确认规则：

- 审批角色、审批层级和授权范围。
- 会计科目、凭证规则和税务口径。
- 合同法律条款和责任边界。
- 预算强制拦截策略。
- 跨公司数据权限。
- 会影响真实业务结果的计算公式。

## 3. 文件规则

### 3.1 存放位置

```text
inputs/md/pages/{业务域}/{页面编码}.md
```

示例：

```text
inputs/md/pages/income/income-contract.md
inputs/md/pages/project/project-setup.md
```

### 3.2 命名规则

- 业务域和文件名使用小写英文及连字符。
- 一个菜单功能对应一个蓝图文件。
- 列表、新增、编辑、详情在同一 HTML 中共用时，只生成一个蓝图。
- 一个业务功能包含多个独立菜单入口时，分别生成蓝图。

### 3.3 蓝图状态

文件开头必须声明状态：

| 状态 | 说明 |
| --- | --- |
| `待确认` | AI 已生成，等待用户检查 |
| `已确认` | 可以生成正式 Schema |
| `需修改` | 用户提出修改，暂时禁止生成 Schema |
| `已变更` | 已确认后发生需求变化，需要重新确认 |

### 3.4 统一模板

所有页面蓝图必须以 `rules/page-blueprint-template.md` 为唯一框架模板。

- 一级章节以及模板标明的固定小节，其名称、编号和顺序必须与模板完全一致。
- 页面差异只能写入对应章节内部；不得新增、删除、改名或移动一级章节和固定小节，补充说明使用正文或加粗标签。
- 不适用的章节或小节必须保留并写明“不适用”。
- “计划输出”统一写入“蓝图信息”，不得另设“预期交付路径”等一级章节。
- 没有依据且会影响业务结果的问题必须列入“待确认项”。

## 4. 标准章节

每个页面蓝图必须按 `rules/page-blueprint-template.md` 的 16 章顺序组织。没有内容的章节也必须说明“不适用”，不能直接遗漏。

### 4.1 蓝图信息

必须包含：

| 项目 | 内容 |
| --- | --- |
| 蓝图状态 | 待确认、已确认、需修改或已变更 |
| 页面名称 | 中文页面名称 |
| 页面编码 | 英文页面编码 |
| 业务域 | 所属业务域 |
| 菜单路径 | 一级菜单/二级菜单 |
| 页面类型 | 列表、详情、列表详情一体、审批、看板、配置等 |
| 生成范围 | 单页面或页面包 |
| 共用范围 | 哪些视图共用一个 HTML |
| 计划输出 | 生成 HTML 的项目相对路径 |
| 参考依据 | 需求、截图、现有页面、组件或业务资料 |

### 4.2 需求理解与 AI 假设

分别列出：

1. 用户明确提出的要求。
2. AI 根据项目规范补充的内容。
3. 暂时无法确定的待确认项。

AI 假设必须显式标记，不能混入已确认需求。

### 4.3 业务目标与范围

必须说明：

- 页面解决什么业务问题。
- 谁在什么情况下使用。
- 本次包含哪些功能。
- 本次明确不包含哪些功能。
- 对业务、项目、合同、预算、收支或凭证产生什么影响。

### 4.4 页面组成与关系

必须列出页面包中的全部视图：

- 列表视图。
- 新增、编辑、查看、审核视图。
- 页签。
- 弹窗和抽屉。
- 数据选择页面。
- 关联页面和穿透入口。

同时说明哪些视图共用一个 HTML，哪些需要独立页面。

### 4.5 页面区域

按用户看到的顺序描述页面区域，例如：

1. 面包屑和页面标题。
2. 查询区域。
3. 页面操作区。
4. 数据列表。
5. 汇总区域。
6. 详情表单。
7. 明细页签。
8. 审批记录。

每个区域必须说明用途、主要组件、默认状态及是否可折叠。

### 4.6 字段定义

查询字段、列表字段、详情字段和明细字段必须分别使用表格描述。

推荐格式：

| 字段 | 控件或展示类型 | 必填 | 只读 | 数据来源 | 规则或说明 |
| --- | --- | --- | --- | --- | --- |
| 合同名称 | 输入框 | 是 | 否 | 用户填写 | 最长 100 个字符 |
| 合同状态 | 状态标签 | 否 | 是 | 系统维护 | 草稿、待审核、已生效 |
| 合同金额 | 金额输入 | 是 | 否 | 用户填写 | 人民币，保留 2 位小数 |

字段定义必须符合 `rules/data-standard.md`。

当业务字段从基础信息移入明细且不再属于整单维度时，蓝图第 6 章必须将其列为“仅明细字段”；正式 Schema 必须通过顶层 `detailOnlyFields` 声明。策略引擎据此自动从查询条件和业务主列表移除同编码字段，禁止仅依赖人工同步。

附件使用 `ProUploadList` 时，策略引擎统一删除重复的内部标题、补齐操作列及删除动作，并通过 `inheritDetailEditability` 继承当前单据编辑状态；页面 Schema 不得用私有实现绕过该策略。

### 4.7 操作定义

页面操作、批量操作和行操作必须分别描述：

| 操作 | 位置 | 可用条件 | 执行结果 | 是否确认 |
| --- | --- | --- | --- | --- |
| 新增 | 列表工具栏 | 有新增权限 | 进入新增视图 | 否 |
| 删除 | 行操作 | 草稿状态 | 删除当前记录 | 是 |
| 审核通过 | 审核页顶部 | 待审核状态 | 状态变为已生效 | 是 |

### 4.8 状态与权限

存在状态变化的页面必须提供状态权限矩阵：

| 状态 | 页面只读性 | 可执行操作 | 可编辑内容 | 下一状态 |
| --- | --- | --- | --- | --- |
| 草稿 | 可编辑 | 保存、提交、删除 | 全部业务字段 | 待审核 |
| 待审核 | 只读 | 通过、驳回 | 审核意见 | 已生效或草稿 |
| 已生效 | 只读 | 查看、业务穿透 | 无 | 不适用 |

没有审批流程时明确写“本页面无审批状态流转”。无流程录入类页面的详情主操作必须定义为“提交”，不得定义为“保存”或“保存草稿”；提交仅保存业务数据并返回列表，不发起审批流程。

### 4.9 业务规则与校验

规则必须写成可以验证的条件，避免“合理校验”“按需要处理”等模糊描述。

推荐格式：

| 编号 | 触发时机 | 条件 | 处理结果 | 提示文案 |
| --- | --- | --- | --- | --- |
| R01 | 提交审核 | 未关联项目 | 阻止提交 | 请至少关联一个已立项项目 |
| R02 | 修改金额 | 计划金额不等于合同金额 | 显示差额 | 收款计划金额必须等于合同金额 |

必须覆盖：

- 必填规则。
- 数据格式和范围。
- 条件显示、条件必填和条件只读。
- 主表与明细表平衡关系。
- 状态操作限制。
- 删除和重大变更确认。
- 业财金额一致性。

### 4.10 关键交互

必须描述可演示的交互结果：

- 查询、重置和展开筛选。
- 列表分页、滚动、冻结和列设置。
- 新增、编辑、查看和返回。
- 页签切换。
- 弹窗、抽屉和数据选择。
- 加载、成功、失败和空状态。
- 条件显示和实时计算。
- iframe 内页面与菜单标签通信。

交互必须符合 `rules/interaction.md`。

### 4.11 业财关联

涉及业务和财务的页面必须说明：

- 所属公司和核算主体。
- 项目归集维度。
- 上游来源单据。
- 下游业务单据。
- 凭证生成或凭证状态。
- 金额一致性和穿透路径。

推荐表达：

```text
已立项项目 -> 收入合同 -> 收款计划 -> 开票申请 -> 收款核销 -> 财务凭证
```

纯配置页或无财务影响的页面可以说明“本页面不直接产生财务数据”。

### 4.12 组件与样例映射

必须优先引用项目已注册组件和现有样例：

| 页面区域 | Schema 组件 | 参考结构 |
| --- | --- | --- |
| 查询区域 | `ProSearchForm` | `prototype-resources/samples/components/pro-search-form.html` |
| 数据列表 | `ProTable` | `prototype-resources/samples/components/pro-table.html` |
| 详情表单 | `DetailForm` | `prototype-resources/samples/components/detail-form.html` |

组件名称必须存在于 `prototype-resources/components/component-registry.json`。不得在蓝图中创造同义重复组件。

同时必须遵循 `rules/resource-center-standard.md`，记录资源中心基线版本、参考页面样例、使用组件和必要差异。

### 4.13 样例数据

蓝图不需要写出完整 JSON 数据，但必须说明：

- 默认记录数量。
- 需要覆盖的状态。
- 需要覆盖的边界场景。
- 金额、日期和编码格式。
- 数据之间必须保持的关联关系。

列表默认使用 12 条高质量业务样例数据，固定每页显示 5 条，不提供页容量选择。

### 4.14 验收标准

验收标准必须可观察、可操作，例如：

- 列表、新增、编辑和详情可在同一 HTML 中切换。
- 正式合同提交前必须通过收款计划平衡校验。
- 试用合同不显示收款计划编辑区域。
- 宽表只在表格区域横向滚动。
- 页面可以直接打开并支持 iframe 嵌入。

不得使用“页面美观”“交互合理”等无法直接判断的表述作为唯一标准。

### 4.15 待确认项

列出尚未解决的具体问题；没有待确认项时写“无”。

存在未解决的关键待确认项时，蓝图状态不能标记为“已确认”。

### 4.16 确认记录

蓝图末尾必须保留确认记录：

| 日期 | 操作人 | 结论 | 说明 |
| --- | --- | --- | --- |
| YYYY-MM-DD | 用户 | 已确认 | 可以生成正式 Schema |

## 5. 页面类型补充要求

| 页面类型 | 必须重点描述 |
| --- | --- |
| 列表页 | 查询条件、列顺序、冻结列、批量操作、分页、行操作 |
| 列表详情一体页 | 列表上下文保留、视图切换、返回行为、共用 HTML 范围 |
| 详情表单页 | 字段分组、编辑模式、只读模式、保存与提交校验 |
| 审批页 | 待办范围、审批动作、意见、状态流转、审批历史 |
| 看板页 | 指标口径、时间范围、图表维度、筛选联动、下钻路径 |
| 配置页 | 配置层级、启停规则、唯一性、影响范围、变更确认 |
| 导入页 | 模板下载、文件限制、数据校验、错误反馈、导入结果 |
| 树表页 | 树层级、节点操作、左右联动、排序和权限继承 |

## 6. 蓝图生成质量要求

AI 生成蓝图时必须满足：

1. 不照抄用户原话，必须补齐页面和业务结构。
2. 不把未经确认的重要假设写成确定规则。
3. 字段、按钮、状态和规则之间必须一致。
4. 列表字段与详情字段应能相互对应。
5. 状态权限必须覆盖所有页面操作。
6. 业财页面必须能够描述业务到财务的穿透链路。
7. 组件必须来自项目组件注册表。
8. 不写实现代码，不把 Schema 混入蓝图。
9. 使用简洁、明确、可检查的中文。
10. 蓝图确认后才能生成正式 Schema。

## 7. Schema 生成前检查清单

- [ ] 蓝图状态为“已确认”。
- [ ] 一级章节和固定小节与 `rules/page-blueprint-template.md` 完全一致。
- [ ] 页面名称、编码、业务域和菜单路径完整。
- [ ] 页面组成和共用 HTML 范围明确。
- [ ] 查询、列表、详情和明细字段完整。
- [ ] 页面操作、批量操作和行操作完整。
- [ ] 已声明是否属于业务维护主列表；属于时默认继承页头批量删除及删除确认规则。
- [ ] 流程详情已覆盖草稿、待审核和只读状态的公共按钮组合。
- [ ] 表单和可编辑明细的必填项可在提交时统一校验。
- [ ] 详情表单桌面端默认使用每行三列布局。
- [ ] 未把固定业务规则设计成常驻解释性横幅；规则优先落实为字段状态和提交校验。
- [ ] 状态、权限和操作条件一致。
- [ ] 业务规则可被程序验证。
- [ ] 条件显示、必填、只读规则明确。
- [ ] 业财关联和金额一致性明确。
- [ ] 使用的组件均已注册。
- [ ] 已引用原型资源中心，并明确参考页面样例和组件。
- [ ] 样例数据覆盖正常、异常和边界状态。
- [ ] 验收标准可以通过页面操作验证。
- [ ] 不存在未解决的关键待确认项。

全部通过后，AI 才能生成 `schemas/pages/{业务域}/{页面编码}.json`。

## 8. 推荐使用方式

用户提出需求：

```text
请根据以下需求生成页面蓝图 MD，遵循 rules/page-blueprint-standard.md。
需求：……
```

用户确认蓝图：

```text
蓝图确认，请生成正式 Schema 和 HTML，并完成检查。
```

用户提出修改：

```text
修改蓝图：……。修改后暂不生成 Schema。
```
